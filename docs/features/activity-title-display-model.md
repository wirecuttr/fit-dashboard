# Activity Title and Display Model

## Summary

FIT Dashboard currently stores and displays a single `activity_name` that often
combines derived location, sport, and sub-sport into one string. That works as a
fallback, but it becomes awkward once an activity has a real title, such as a
Garmin planned workout name, a TrainerRoad workout name synced into Garmin, or a
user-entered title.

This feature proposes separating activity title concepts from derived location
and activity type context. The goal is to make names closer to Garmin Connect and
Strava behaviour without losing useful sport/sub-sport information in the UI.

## Problem

Today, generated names can collapse multiple concepts into one field:

```text
Calgary, Alberta - Road Cycling
Calgary, Alberta - Indoor Cycling
Calgary, Alberta - eBiking
```

Those strings are not true activity titles. They are generated display labels.
When a real title exists, using location as the primary name is not ideal.
Garmin Connect and Strava generally show a real activity title first and use
icons, sport labels, and secondary metadata for context.

Examples:

```text
Garmin planned workout:
Title: Stickney
Type/context: Indoor Cycling
Location/context: Calgary

No real title:
Title: Calgary Road Cycling
Type/context: cycling icon and/or Road Cycling
```

## Related Work

Feature 33, Garmin planned workouts, should preserve `Workout.wkt_name` and
related workout metadata. That gives FIT Dashboard a reliable `source_title` for
some activities, but it should not by itself redesign all activity naming.

This feature owns the broader display model:

- user-entered titles
- source/workout titles from imported files
- generated fallback titles
- location labels
- sport/sub-sport display labels
- sport icons as primary type indicators
- export semantics and migration behaviour

## Goals

- Treat real titles as primary when available.
- Use generated location/type names only as fallbacks.
- Keep sport/sub-sport visible without forcing it into every title.
- Prefer city-level primary fallback names, such as `Calgary Road Cycling`, over
  heavier names such as `Calgary, Alberta - Road Cycling`.
- Preserve raw imported metadata such as `sport`, `sub_sport`, and
  `Workout.wkt_name` without baking current display wording into stored values.
- Avoid overwriting existing user-edited names.
- Keep the first implementation compatible with existing data.

## Non-Goals

- Full automatic reverse parsing of existing generated `activity_name` values.
- Backfilling or rewriting existing activity names without a user-controlled
  migration path.
- Changing Feature 33's initial planned-workout interval-table scope.
- Replacing all sport text with icons. Icons should carry the primary type cue,
  but text labels remain useful for accessibility, search, export, and compact
  metadata.

## Proposed Concepts

Separate the display model into these concepts:

```text
user_title
  A title entered or edited by the FIT Dashboard user.

source_title
  A title imported from the source file or source metadata.
  Examples: Workout.wkt_name = Stickney, Sprint, Total Body Circuit 3.

generated_title
  A fallback title generated by FIT Dashboard when no real title exists.
  Example: Calgary Road Cycling.

location_label
  Human-readable location context derived from GPS.
  Example: Calgary, Alberta.

location_city
  City-level location used for compact generated titles.
  Example: Calgary.

location_region
  Region/province/state context, used as secondary metadata when helpful.
  Example: Alberta.

activity_type_label
  Display label derived from sport/sub_sport.
  Examples: Road Cycling, Indoor Cycling, eBiking, Trail Running.

sport_icon
  Primary visual type indicator derived from sport, and possibly sub_sport.
```

`activity_type_label` should generally be derived at display time from raw
`sport` and `sub_sport`. Labels can improve over time, so storing only the final
wording risks making old imports stale.

## Display Priority

Primary title resolver:

```text
user_title
source_title
generated_title
file_name fallback
```

Generated title resolver:

```text
if location_city and activity_type_label:
    generated_title = "{location_city} {activity_type_label}"
elif activity_type_label:
    generated_title = activity_type_label
else:
    generated_title = file_name without extension
```

Examples:

```text
Real workout title:
[cycling icon] Stickney
Indoor Cycling - Calgary

User-renamed activity:
[cycling icon] Easy spin before work
Indoor Cycling - Calgary

No real title, GPS available:
[cycling icon] Calgary Road Cycling
Garmin Edge 1040 - Jun 28 - 102 km

No real title, no GPS:
[cycling icon] Indoor Cycling
Garmin Edge 1040 - 1h00m
```

## UI Direction

Garmin Connect can show short titles because the sport icon is a primary activity
type indicator. FIT Dashboard should move in the same direction before relying
heavily on short source titles.

Recommended UI structure:

```text
Row/header leading icon:
  sport_icon

Primary text:
  resolved title

Secondary text:
  activity_type_label, location_city/location_label, device, date/time,
  duration/distance as space allows
```

The activity list and detail header should not need to put location, sport, and
sub-sport all into the primary title when a real title exists.

## Import and Storage Direction

Initial non-breaking direction:

- Keep existing `activity_name` for compatibility.
- Add nullable structured fields later, rather than changing meaning abruptly.
- Preserve raw metadata needed to compute labels.
- Use a display resolver that prefers structured fields when present and falls
  back to existing `activity_name` when they are absent.

Possible future database fields:

```text
user_title TEXT NULL
source_title TEXT NULL
generated_title TEXT NULL
location_city TEXT NULL
location_region TEXT NULL
location_country TEXT NULL
location_label TEXT NULL
```

Alternative naming:

```text
activity_title / user_title
source_activity_title
derived_activity_title
```

The exact column names should be chosen during implementation, but the important
point is that real titles, generated fallback titles, and location context are
not the same concept.

## Migration Strategy

Do not aggressively reverse-map existing `activity_name` values. Existing names
may have been edited by users, and strings like `Calgary, Alberta - Road Cycling`
can be ambiguous.

Suggested migration approach:

1. Add nullable structured columns.
2. New imports populate structured fields.
3. Existing rows display through fallback logic using `activity_name` until they
   are reimported, edited, or migrated by an explicit future tool.
4. If the app can identify user-edited titles reliably later, add a controlled
   migration/backfill option.

## JSON Export Considerations

Current JSON export emits the stored `activity.activityName`. Once structured
fields exist, export should avoid hiding the distinction between real and
generated names.

Possible export shape:

```json
{
  "activity": {
    "activityName": "Stickney",
    "title": "Stickney",
    "sourceTitle": "Stickney",
    "generatedTitle": "Calgary Indoor Cycling",
    "location": {
      "label": "Calgary, Alberta",
      "city": "Calgary",
      "region": "Alberta",
      "country": "Canada"
    },
    "sport": "cycling",
    "subSport": "indoor_cycling",
    "activityTypeLabel": "Indoor Cycling"
  }
}
```

For compatibility, `activityName` can remain the resolved display title while
new fields expose why that title was chosen.

## Relationship to Feature 33

Feature 33 should parse and preserve planned-workout metadata, including
`Workout.wkt_name`. It should not need to decide the full display-title model.

This feature can later consume that metadata:

```text
Feature 33:
  Workout.wkt_name -> source_title metadata

This feature:
  source_title becomes primary title when no user_title exists
```

Until this feature is implemented, Feature 33 can leave activity-name behaviour
unchanged and still preserve the data needed for future display improvements.

## Open Questions

- Should `activity_name` eventually become `user_title`, or remain a legacy
  resolved display value?
- How should the app identify existing user-edited names?
- Should city-only generated titles always omit province/region, or should the
  UI add region for ambiguous city names?
- Which sport/sub-sport icons are needed for a useful first pass?
- Should source titles from non-FIT formats be supported later?
- Should the search index store resolved title, source title, location, and
  activity type as separate searchable fields, or collapse them into one search
  string?
