# Activity Title and Display Model

## Summary

FIT Dashboard currently stores and displays a single `activity_name` that often
combines derived location, sport, and sub-sport into one string. That works as a
fallback, but it becomes awkward once an activity has a real title, such as a
Garmin planned workout name, a TrainerRoad workout name synced into Garmin, or a
user-entered title.

This feature proposes separating activity title concepts from derived location
and activity type context. The goal is to make names closer to Garmin Connect and
Strava behaviour without losing useful sport/sub-sport information in the UI.

## Problem

Today, generated names can collapse multiple concepts into one field:

```text
Calgary, Alberta - Road Cycling
Calgary, Alberta - Indoor Cycling
Calgary, Alberta - eBiking
```

Those strings are not true activity titles. They are generated display labels.
When a real title exists, using location as the primary name is not ideal.
Garmin Connect and Strava generally show a real activity title first and use
icons, sport labels, and secondary metadata for context.

Examples:

```text
Garmin planned workout:
Title: Stickney
Type/context: Indoor Cycling
Location/context: Calgary

No real title:
Title: Calgary Road Cycling
Type/context: cycling icon and/or Road Cycling
```

## Related Work

Feature 33, Garmin planned workouts, should preserve `Workout.wkt_name` and
related workout metadata. That gives FIT Dashboard a reliable `source_title` for
some activities, but it should not by itself redesign all activity naming.

This feature owns the broader display model:

- user-entered titles
- source/workout titles from imported files
- generated fallback titles
- location labels
- sport/sub-sport display labels
- activity type labels as primary type indicators, with optional future icons
- export semantics and migration behaviour

## Goals

- Treat real titles as primary when available.
- Use generated location/type names only as fallbacks.
- Keep sport/sub-sport visible without forcing it into every title.
- Prefer city-level primary fallback names, such as `Calgary Road Cycling`, over
  heavier names such as `Calgary, Alberta - Road Cycling`.
- Preserve raw imported metadata such as `sport`, `sub_sport`, and
  `Workout.wkt_name` without baking current display wording into stored values.
- Avoid overwriting existing user-edited names.
- Prefer the clearest long-term data model. Keep old behaviour only where it
  reduces risk, avoids unnecessary migrations, or makes the implementation
  simpler.

## Non-Goals

- Full automatic reverse parsing of existing generated `activity_name` values.
- Backfilling or rewriting existing activity names without a user-controlled
  migration path.
- Changing Feature 33's initial planned-workout interval-table scope.
- Building a complete activity icon system in the first implementation. The app
  does not currently have sport/sub-sport icons, and text labels remain required
  for accessibility, search, export, and compact metadata.

## Proposed Concepts

Separate the display model into these concepts:

```text
activity_name / activity_title
  `activity_name` remains the implementation field for the displayed,
  user-editable activity title. `activity_title` is the conceptual name for that
  role in this design. The value is set at import time to the best available
  default, then changes only when the user edits the activity name.

source_title
  A title imported from the source file or source metadata.
  Examples: Workout.wkt_name = Stickney, Sprint, Total Body Circuit 3.

generated_title
  A fallback title generated by FIT Dashboard from location and activity type.
  It is stored for provenance and future reuse, even when `activity_title` /
  `activity_name` is later edited by the user. Example: Calgary Road Cycling.

location_label
  Human-readable location context derived from GPS.
  Example: Calgary, Alberta.

location_city
  City-level location used for compact generated titles.
  Example: Calgary.

location_region
  Region/province/state context, used as secondary metadata when helpful.
  Example: Alberta.

activity_type_label
  Primary text activity type indicator derived from sport/sub_sport.
  Examples: Road Cycling, Indoor Cycling, eBiking, Trail Running.

activity_icon_key
  Optional future visual cue derived from sport/sub_sport. The first
  implementation should not depend on icons. If icons are added later, they
  should be sub-sport aware, for example road cycling vs indoor cycling vs
  mountain biking.
```

`activity_type_label` should generally be derived at display time from raw
`sport` and `sub_sport`. Labels can improve over time, so storing only the final
wording risks making old imports stale.

## Title Defaulting

The app should resolve the editable display title at import time:

```text
source_title = imported source/workout title, if present
generated_title = app-generated fallback title
activity_title = source_title ?? generated_title ?? file_name fallback
```

Implementation decision: keep using the existing `activity_name` field for this
concept rather than renaming it in the first implementation:

```text
activity_name = source_title ?? generated_title ?? file_name fallback
```

After import, the UI displays `activity_name` / `activity_title`. If the user
edits the activity name, only that displayed title changes; `source_title` and
`generated_title` remain as reference/provenance fields. UI surfaces can treat an
`activity_name` that differs from `generated_title` as an independent title and
show type/location context around it.

Generated title resolver:

```text
if location_city and activity_type_label:
    generated_title = "{location_city} {activity_type_label}"
elif activity_type_label:
    generated_title = activity_type_label
else:
    generated_title = file_name without extension
```

Examples:

```text
Garmin planned workout:
source_title = Stickney
generated_title = Calgary Indoor Cycling
activity_name = Stickney

User-renamed planned workout:
source_title = Stickney
generated_title = Calgary Indoor Cycling
activity_name = Easy spin before work

No real title, GPS available:
source_title = null
generated_title = Calgary Road Cycling
activity_name = Calgary Road Cycling

No real title, no GPS:
source_title = null
generated_title = Indoor Cycling
activity_name = Indoor Cycling
```

## UI Direction

The main UI target for this feature is the left-side activity list. The list is
where users scan many activities quickly, and it does not have the map visible.

Recommended left-side list row structure:

```text
Primary text:
  activity_name / activity_title

Type indicator:
  activity_type_label, shown as compact text or an existing badge-like treatment

Secondary text:
  date/time, duration/distance, device, and location when useful
```

Sample list outcomes:

```text
Stickney
Indoor Cycling - Calgary - 1h15m

Easy spin before work
Indoor Cycling - Calgary - 45m

Calgary Road Cycling
Road Cycling - 102 km - Garmin Edge 1040

Indoor Cycling
Garmin Edge 1040 - 1h00m
```

The Individual activity page has different needs. It already shows sub-sport and
main device as badges in the activity header, and activities with GPS already
have a map on the page. This feature should not add redundant type, device, or
location text to the Individual header. The Individual page should mainly use
the resolved `activity_name` / `activity_title` as its primary title and keep the
existing badges for context.

Icon support is optional future work. Garmin uses sub-sport-level icons, so a
useful icon system would need mappings such as road cycling, indoor cycling,
mountain biking, gravel cycling, trail running, treadmill running, and track
running. Until that exists, `activity_type_label` is the primary activity type
indicator.

## Import and Storage Direction

Implementation principle: choose the storage model that makes titles explicit and
easy to reason about. Do not keep a compatibility layer unless it directly helps
the implementation or protects user-entered data.

Implementation decision:

- Keep the existing `activity_name` column as the displayed editable activity
  title. Renaming it would touch the schema, Rust models, insert/list/update
  paths, frontend types, UI surfaces, exports, compare charts, and overview
  tables without changing user-visible behaviour.
- Add `source_title` and `generated_title` as provenance/reference fields.
- Add location columns so generated titles and the left-side list do not need to
  reverse-parse `activity_name` or recompute location context.
- Add a `sub_sport` column so activity type labels can be derived from raw
  imported values instead of stored display wording.
- Preserve raw metadata needed to compute labels.
- Resolve the displayed title at import time rather than requiring every UI
  surface to repeat the same fallback chain.

Database fields:

```text
activity_name TEXT NOT NULL
source_title TEXT NULL
generated_title TEXT NULL
sport TEXT NULL
sub_sport TEXT NULL
location_city TEXT NULL
location_region TEXT NULL
location_country TEXT NULL
location_label TEXT NULL
```

The important point is that the displayed editable title, imported source title,
generated fallback title, raw activity type values, and location context are not
the same concept.

## Migration Strategy

Do not preserve old behaviour for its own sake. If a database migration or
meaningful model change makes the implementation simpler and more correct, it is
acceptable.

Still avoid aggressive reverse-mapping of existing `activity_name` values unless
there is a clear benefit. Existing names may have been edited by users, and
strings like `Calgary, Alberta - Road Cycling` can be ambiguous.

Migration approach:

1. Add the structured fields above.
2. New imports populate structured fields.
3. Existing rows are not backfilled or reverse-parsed; assume reimport for users
   who want structured title/location provenance on older activities.
4. Existing `activity_name` values remain displayed as-is until an activity is
   reimported or edited.
5. If the app can identify user-edited titles reliably later, add a controlled
   migration/backfill option.

## JSON Export Considerations

Current JSON export emits the stored `activity.activityName`. Once structured
fields exist, export should avoid hiding the distinction between the displayed
editable title, source title, and generated title.

Possible export shape if the DB keeps `activity_name` as the displayed title:

```json
{
  "activity": {
    "activityName": "Stickney",
    "sourceTitle": "Stickney",
    "generatedTitle": "Calgary Indoor Cycling",
    "location": {
      "label": "Calgary, Alberta",
      "city": "Calgary",
      "region": "Alberta",
      "country": "Canada"
    },
    "sport": "cycling",
    "subSport": "indoor_cycling",
    "activityTypeLabel": "Indoor Cycling"
  }
}
```

For this implementation, `activityName` should remain the exported displayed
title, matching the retained `activity_name` implementation field. The additional
fields expose source/generated provenance without changing the primary export
name.

## Relationship to Feature 33

Feature 33 should parse and preserve planned-workout metadata, including
`Workout.wkt_name`. It should not need to decide the full display-title model.

This feature consumes that metadata when available:

```text
Feature 33:
  Workout.wkt_name -> source_title metadata

This feature:
  source_title becomes the default activity_name / activity_title when present
```

If this branch is implemented before Feature 33 is merged upstream, the
implementation must either duplicate the small `Workout.wkt_name` extraction
needed for `source_title`, or wait/rebase after Feature 33 lands. The title model
itself does not require the full planned-workout interval-table feature.
